一、项目定位与设计原则

本应用面向全球华人（含中国港澳台、东南亚、北美、欧洲等地华语群体），目标是在单一权威来源之上，提供可信赖的中文信仰内容与健康生活指导。其根本约束是：所有源内容必须以英文原版为准，严禁以任何现有中文译本作为翻译或教义的凭据。

权威来源（Source of Truth）

  • KJV 英文圣经（King James Version, 1611）—— 圣经文本的唯一权威底本。
  • 怀爱伦（Ellen G. White）全部原版英文著作 —— 教义阐释与健康教导的权威补充，须取原文。
  • 复临安息日会官方教义 —— 以教会正式公布的《28 条基本信仰》等官方英文文献为准。

六大设计原则

① 原文溯源

每一句中文都必须能追溯到具体的 KJV 经文 / EGW 段落 / 教义条款编号。

② 可追溯翻译

中文由"原文→中文"的管线生成并经审核，而非从和合本等既有译本回译。

③ RAG 增强

问答与讲解基于检索增强生成，答案必须引用权威段落，避免模型臆测。

④ 专家在环

所有对外内容上线前需经合格神学 / 医学顾问审核放行。

⑤ 离线优先

核心圣经、译本、教义预置本地，无网络也能读；EGW 文库可下载。

⑥ 表述克制

对照标注以"释经观察"呈现差异，保持学术与牧养分寸，而非论战口吻。

关于"和合本"的对照：应用自身的中文译本是独立从原文生成的；仅在"对照 / 注释"功能里，将和合本作为被观察的参照对象展示差异，但绝不作为真理来源。这一区分对版权与神学可信度都至关重要。

二、整体架构

采用分层 + 客户端 / 服务端分离的架构。客户端统一用一套代码覆盖全平台；服务端负责内容管理、检索与受控的 AI 推理；AI 推理层以"检索增强（RAG）"为核心，确保一切生成内容都锚定在权威原文之上。

技术选型

层级推荐技术理由
客户端Flutter 3.x（Dart）一套代码编译到 iOS/Android/Windows/macOS/Linux/Web，原生体验，桌面支持成熟。
后端服务Python FastAPI + PostgreSQLAI/RAG 生态最完善；异步高性能；便于与向量库、模型服务集成。
向量检索pgvector（或 Qdrant/Milvus）与 Postgres 同库，运维简单；支持语义 + 混合检索。
本地存储SQLite + FTS5移动/桌面离线全文检索；小体积、零配置。
生成模型可自托管中文 LLM（如 Qwen 系列）+ RAG内容敏感，自托管保障隐私与可控；中文能力强。
内容管理内部审核台（Web 管理后台）专家提交、比对、审批、版本发布。

三、核心模块划分

模块 A · 圣经中文翻译与对照

  • 独立译本库：从 KJV 原文逐节生成中文，译文与原文逐节绑定，形成"本应用官方中文译本"。
  • 对照阅读：并排显示 KJV 英文、本应用中文、以及（仅作参照的）和合本，供用户直观比较。
  • 差异注释：由神学顾问撰写"释经注记"，说明某节在 KJV 与和合本之间的关键用词 / 句式差异及其原文依据。注记以客观释经语言书写，不采用攻击性措辞。
  • 术语词典：统一关键神学词汇（如 justification、sanctification、sabbath 等）的译法，全库一致。

模块 B · 牧师问答（信仰与教义）

  • 资深牧师人格：以"资深牧者"语气作答——准确、通俗、有同理心，引用 KJV/EGW/教义原文。
  • 教义问答：基于《28 条基本信仰》与 EGW 著作回答安息日、救恩、预言、教会治理等问题。
  • 偏差纠正：当问题涉及个别牧者 / 传道人的常见误解时，系统据权威原文澄清正确立场，对事不对人，只指出"某观点与权威来源不符"，不下人格判断。
  • 引用强制：每条回答必须附权威段落出处（书卷/章节/节，或 EGW 著作+段落，或教义条款编号）。

模块 C · 健康生活指导

  • 饮食指导：依据 EGW《服务真诠》《饮食证言》《节制》等及圣经，倡导以植物性饮食为主的均衡营养；说明原理而非绝对律法。
  • 心理健康：基于 EGW 关于休息、自然、信心、社群、节制等教导，提供压力管理、情绪调节、灵修节律建议。
  • 全人健康（NEWSTART 框架）：Nutrition（营养）、Exercise（运动）、Water（水）、Sunlight（阳光）、Temperance（节制）、Air（空气）、Rest（休息）、Trust（信靠）——每条对应权威出处与可执行建议。
  • 个人追踪（可选）：饮水、睡眠、运动打卡与提醒；附医疗免责声明，明确"非专业医疗建议，疾病请就医"。

四、数据与内容来源（全部基于英文原版权威材料）

所有内容管线的"源头"均为英文原版。中文是产出物，不是来源。下表明确每条数据的权威出处与获取方式。

数据类别权威来源（英文原版）版权状态（需法务复核）结构化方式
圣经文本 KJV (1611)，公共领域。可从标准公开文本库获取逐节结构化数据。 公共领域，可自由使用 书→章→节三级 ID，附原文、分词、词形
怀爱伦著作 EGW 原版英文著作：如 Steps to Christ, The Great Controversy, Desire of Ages, Ministry of Healing, Counsels on Diet and Foods, The Ministry of Healing, Temperance 等。 EGW 卒于 1915 年，原版文本在多数司法辖区已进入公共领域；但现代汇编版 / 译本 / 排版可能仍受 White Estate 版权保护 → 须法务界定可用范围。 著作→章节→段落三级 ID，保留原始出版元数据
教会教义 SDA 官方英文文献：《28 Fundamental Beliefs》、官方年鉴与立场声明（英文原版）。 教会公开发布，宜以官方英文原版为准并注明出处 条款编号 + 标题 + 正文段落

版权红线：严禁将和合本（及其版权方授权文本）的译文作为本应用的翻译来源或训练依据。EGW 现代汇编本与官方中文材料同样不可直接抓取使用。任何进入内容库的材料都须经法务确认"可作原文底本使用"。

内容处理管线

英文原版权威文本（KJV / EGW / 教义） ↓ 结构化（切分 + 编号 + 元数据） ↓ 中文翻译（翻译模型 + 术语词典约束） ↓ 神学顾问审核（溯源核对、术语一致、无增删） ↓ 向量化（embedding）+ 入库 ↓ 发布（版本号 + 变更日志） ↓ 客户端差分同步 / 离线包

五、内容准确性校验机制

准确性是本项目生命线。采用"技术校验 + 专家在环 + 全程溯源"三重保险。

1. 溯源绑定（每句可追）

  • 每条中文译文在数据库中记录 source_id（KJV 节 ID / EGW 段落 ID / 教义条款 ID）。
  • 前端展示译文时，可一键展开"原文出处"，做到透明可查。

2. 自动化校验（上线前拦截）

  • 反向语义一致性：将中文译文回嵌为向量，与原文向量比对，相似度低于阈值即告警（防漏译 / 跑题）。
  • 术语一致性：术语词典强制统一译法，自动扫描违例。
  • 无增删检测：译文不得引入原文没有的神学断言；与原文事实性陈述做对齐检查。
  • 引用必填：问答输出若无有效 source_id 锚定，系统拒绝直接发布，转人工。

3. 专家在环（人工终审）

  • 设立神学顾问组（合格 SDA 神职 / 学者）与医学顾问组（注册营养师 / 医师）分别把关信仰内容与健康内容。
  • 审核台提供"原文 + 机译 + 专家建议译"三栏对照，审批后打版本号发布。
  • 健康模块所有建议须经医学顾问确认，避免越界成"医疗诊断"。

4. 运行时防护（问答 RAG）

  • 问答只在检索到的权威片段内作答；禁止脱离上下文的自由发挥。
  • 输出附置信度与引用片段；低置信 / 无引用时提示"建议咨询本地面牧者"。
  • 用户可对回答"纠错 / 上报"，进入顾问复核队列，形成闭环。

5. 版本与审计

  • 内容库全程版本化（类似 Git），每次变更留痕：谁、何时、基于哪版原文、改了什么。
  • 出现偏差可一键回滚到已审版本。

六、跨平台实现方式

核心策略：一套 Flutter 代码 + 本地离线库 + 轻量云端同步，让手机与电脑体验一致、数据贯通。

统一客户端（Flutter）

  • 同一 Dart 代码库编译为：iOS App、Android App、Windows/macOS/Linux 桌面应用、以及 Web 应用。
  • 响应式布局：手机单列、桌面多栏（如左侧圣经导航 + 中间经文 + 右侧注释）。
  • 共享业务逻辑（翻译对照、RAG 问答、健康打卡），避免各端重复实现。

离线优先

  • 首次安装预置 SQLite + FTS5：KJV 原文、本应用中文译本、教义条款，开箱即读。
  • EGW 文库较大，提供"按需下载"整本或分卷包。
  • 无网络时：阅读、检索、已缓存的健康内容全部可用；问答仅限离线缓存的 FAQ。

云端同步（有网时）

  • 账号体系（邮箱 / 第三方）同步：书签、笔记、健康打卡、个性化设置。
  • 内容更新以差分包下发，减少流量；版本号对齐服务端。
  • 问答等高算力任务走服务端 RAG；端侧仅做展示与缓存。

桌面端特别处理

  • Windows/macOS 支持窗口缩放、键盘快捷翻节、打印 / 导出经文与笔记为 PDF。
  • Linux 提供 AppImage / deb 包，便于海外华人社区分发。

七、风险与合规提示

① 版权风险（最高优先级）：EGW 著作的现代汇编版、官方译本、以及和合本均可能受版权保护。务必在法务确认"哪些英文原版文本可自由作为底本"后再抓取入库。绝不可把既有中文译本的文本 / 译文作为本应用来源。
② 表述分寸："指出和合本偏差"与"纠正个别牧者"功能，建议以释经观察 + 对事不对人的方式呈现，只陈述"某表述与 KJV/EGW/教义原文的差异及依据"，避免论战化、人身化表述，以保障可信度与跨地区合规。
③ 医疗边界：健康模块是"生活指导"而非"医疗诊断"。须明确免责声明，并建议用户重大健康问题咨询专业医师。
④ AI 幻觉：通过 RAG 溯源 + 引用必填 + 低置信转人工，将模型臆测风险降到最低；但人工终审仍是不可替代的一道闸。

八、落地路线建议

  1. 阶段 0 · 法务与授权（2–4 周）：界定可合法使用的英文原版范围，签署必要授权，建立"白名单来源库"。
  2. 阶段 1 · 内容中台（6–8 周）：搭建结构化内容库 + 翻译审核台 + 向量索引，先完成 KJV 全本与《28 条信仰》入库。
  3. 阶段 2 · 客户端 MVP（8–10 周）：Flutter 实现模块 A（翻译对照）+ 离线阅读，双端（Android/iOS）内测。
  4. 阶段 3 · 牧师问答（6–8 周）：接入 RAG 管线 + 顾问终审，灰度发布模块 B。
  5. 阶段 4 · 健康模块（6 周）：医学顾问审核后上线模块 C，含 NEWSTART 框架与个人追踪。
  6. 阶段 5 · 全平台与分发（4 周）：补齐桌面端 / Web，上线应用商店与教会社区分发渠道。
本方案将"以英文原版为唯一权威"作为架构级约束（溯源绑定 + 不依赖中文译本），并通过 RAG 与专家在环保障准确性。下一步若你确认，我可以：① 把阶段 1 的内容库 schema 设计成可落地的数据表；② 画出模块 B 的 RAG 问答时序图；③ 起草一份给法务的"可用英文原版白名单"清单。
