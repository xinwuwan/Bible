一、MVP 范围与切片

本 MVP 目标：交付一个离线可用、内容可信、三核心模块均有最小可用切片的跨平台应用，验证「英文权威 → 独立中文产出 → 多端一致体验」这条主链路，而非一次做全。所有中文内容一律来自本应用自产，不依赖任何既有中文译本作为来源。

1.1 三大模块的最小可用定义（MVP 切面）

模块MVP 做到暂不做（Out of Scope）
A 翻译与对照 KJV 全本 + 新约（或全本）逐节独立中文译本；并排展示 KJV / 本应用中文 / 和合本（仅参照）；释经注记（comparison_note）含 pilot 30 条 + 持续扩充 全本 66 卷一次性精校；音频朗读；多译本切换引擎
B 牧师问答 RAG 问答：检索 KJV+EGW+教义；结构化输出 answer_zh / citations / confidence / needs_human；校验闸门（引用必填 + 置信阈值）；低把握转人工 多轮深度对话记忆；个性化释经辅导；实时语音问答
C 健康指导 NEWSTART 八支柱内容 + 权威来源绑定；结构化指导条目；每日打卡（health_log_entry）；医疗免责强制展示 接入穿戴设备；营养计算卡路里；与医生系统互联
平台 Flutter 一套代码覆盖 iOS / Android / Windows / macOS / Web；离线优先（预置 SQLite 圣经+译本+教义）；轻量云同步（书签/笔记/打卡） Linux 发行包、电视端、小程序

1.2 非功能硬性约束（贯穿全程）

  • 红线 任何对外中文内容必须可溯源到权威英文原文（source_id），禁止把和合本或任何中文译本当来源。
  • 版权 上线前须由法务完成 Tier 1 白名单裁定（见 legal-whitelist-and-health 文档）；Tier 2 健康汇编改用 EGW 生前 PD 单篇重汇编。
  • 离线 首屏与圣经阅读零网络依赖；EGW 文库按需下载；RAG 问答需联网（可降级为本地索引检索）。
  • 可信 医疗/教义内容未过医学/神学审核不可发布；所有发布内容版本化、可回滚。

二、技术栈与基础设施约定

后端

  • API 服务FastAPI（Python 3.11+）或 NestJS；推荐 FastAPI（与 pgvector / transformers 生态一致）
  • 数据库PostgreSQL 15+ + pgvector 0.5+
  • 向量模型BAAI/bge-small-zh-v1.5（512 维，与 rag-example 对齐）；仅索引权威原文
  • LLM 网关优先自托管中文模型（Qwen2.5 / ChatGLM3 7B+）；外网兜底可选合规云 API
  • 缓存Redis（会话/限流/检索缓存）
  • 对象存储EGW 文库按需分片、离线包分发

前端

  • 框架Flutter 3.22+（Dart 3）
  • 本地库SQLite + FTS5（离线圣经/译本/教义全文检索）；drift 或 sqlite3 包
  • 状态Riverpod（Provider 家族，适合多页共享书签/会话）
  • 网络dio + retrofit（类型化 API 客户端）
  • 同步差量同步：本地 last_seq 游标 + 云端 versioned patch

工程化

  • CIGitHub Actions：lint + 单测 + 多端 build 冒烟
  • SchemaAlembic（Python）或 Flyway 做 DB 迁移，与 schema-and-rag DDL 对齐
环境约定：开发/预发/生产三环境隔离；DATABASE_URL、LLM_GATEWAY_URL、EMBEDDING_MODEL 一律走环境变量，禁止硬编码；密钥不入仓库。客户端与 API 的契约以本文档第五节为单一事实来源（single source of truth）。

三、阶段排期甘特图（24 周）

排期从 2026 年 11 月初 起算（前置法务/内容冻结 P0 与 M1 并行启动）。每个阶段标注里程碑产出与验收要点。

关键依赖链：M1 数据层必须先于 M3/M4 完成（权威库 + 中文产出 + 向量索引就绪）；M2 客户端骨架与 M1 并行；M3 完成后模块 A 即可灰度；M4 依赖 M1 的 content_chunk 向量表；M5 与 M4 部分重叠；M6 收口审核与公测。

四、分阶段任务拆解

P0 · 法务与内容冻结（W0–3，前置）

  • 法务裁定：依白名单文档确认 Tier 1 可用清单（KJV 1611 + EGW 生前 PD 原版）；Tier 2 健康汇编改用生前 PD 单篇重汇编；出具英联邦 KJV 区域处理方案。
  • 权威文本采集：编写采集脚本抓取/导入 KJV 逐节、EGW 生前原版逐段、28 条教义英文原版；生成 content_chunk 切片与向量（bge-small-zh-v1.5, 512 维）。
  • 验收：白名单通过法务签字；权威库条数核对（KJV ≈ 31,102 节；EGW 段落按书）；向量维度一致。

M1 · 数据层与基础设施（W1–5）

  • 执行 schema-and-rag 文档的全部 DDL（8 组表）；建立 Alembic 迁移基线。
  • 落地「中文产出外键回源」约束（所有 *_zh 表外键指向英文来源表）；和合本写入独立 bible_verse_cuv_ref，不参与推理。
  • 搭建 FastAPI 骨架、Redis、对象存储；API 鉴权中间件（JWT 设备登录）。
  • 验收：DB 约束测试通过（尝试以中文反推来源被拒）；内容发布走 content_version 版本化。

M2 · 客户端骨架 + 离线圣经阅读（W3–9）

  • Flutter 工程初始化（多端 target）；Riverpod 状态层；dio 类型化客户端。
  • 构建离线 SQLite 包（预置 KJV + 本应用中文 + 教义），含 FTS5 全文检索；首版阅读器（书卷/章/节导航、夜间模式、字号）。
  • 书签、笔记本地存储；差量同步骨架（last_seq 游标）。
  • 验收：断网状态下完整阅读圣经 + 全文检索可用；书签本地持久化。

M3 · 模块 A 翻译对照（W6–13）

  • 后端：GET /bible/... 与 GET /compare/verses，并排返回 KJV / our_zh / cuv_ref / comparison_note。
  • 前端：对照阅读页（三栏/可切换）、comparison_note 卡片展示。
  • 接入 pilot 30 条对照注记（comparison-note-pilot 文档），走 review_queue 审核流；其余章节标记「注记待补充」。
  • 验收：对照页离线可用；注记必须含 basis 字段且来源 id 有效；和合本仅展示不参与推理。

M4 · 模块 B 牧师问答 RAG（W10–19）

  • 检索服务：混合检索（向量 + 关键词）→ 重排 → 阈值过滤（对齐 schema-and-rag 时序图）。
  • LLM 网关：注入 master-handbook 第八章的「系统人格 + 检索上下文 + few-shot」，输出结构化 JSON。
  • 校验闸门：引用必填、置信 < 0.70 或 needs_human 转人工、来源 id 必须存在于 content_chunk、出现和合本 id 直接拦截、敏感词触发复核。
  • 前端：问答页 + 引用锚点跳转 + 「转人工/纠错反馈」入口（写 review_queue + qa_feedback）。
  • 验收：100 条探针问题，引用缺失率 = 0；误答（无来源臆测）拦截率 100%；转人工链路联通顾问台。

M5 · 模块 C 健康指导（W14–21）

  • 落 NEWSTART 5 张表；八支柱内容与权威来源绑定（复用模块 A/B 同一权威库）。
  • health_guidance 条目带 evidence_level + medical_reviewed 闸门；每条强制医疗免责。
  • 前端：健康首页（八支柱）、指导详情、每日打卡（health_log_entry）、趋势。
  • 验收：未过 medical_reviewed 的条目不可见；免责文案 100% 展示；打卡数据同步。

M6 · 审核发布台 + 公测上线（W19–24）

  • 顾问台：review_queue 审批流（comparison_note / 问答纠错 / 健康条目）；content_version 可回滚。
  • 灰度发布（小范围华人团契）+ 反馈收集；性能/崩溃监控。
  • 英联邦区域 KJV 替代方案（ASV/WEB）开关；多语言 UI 占位（粤语/繁体）。
  • 验收：审核台全流程跑通；崩溃率 < 1%；法务合规复查通过。

五、后端 API 接口契约

基址 /api/v1，统一 JSON；鉴权 Authorization: Bearer <JWT>。错误统一体：{"error":{"code":"...","message":"..."}}。常用错误码：401 未认证 / 403 无权 / 404 不存在 / 422 参数错误 / 429 限流 / 500 服务错误。

5.1 认证

方法 / 路径说明请求响应（要点）
POST /auth/device 设备匿名登录拿 JWT（不强制注册） {device_id, platform} {token, role:"anonymous|member"}

5.2 圣经与对照（模块 A）

方法 / 路径说明响应（要点）
GET /bible/books 书卷目录 {books:[{id, name_en, name_zh, chapters}]}
GET /bible/books/{book}/chapters/{ch}/verses 某章全部节（KJV + 本应用中文 + 和合本参照） {book, chapter, verses:[{verse, kjv_text, our_zh, cuv_ref_text}]}
GET /compare/verses?refs=Jn3:16,Ro3:23 对照 + 释经注记 {items:[{ref, kjv_text, our_zh, cuv_ref_text, note:{diff_type, observation, basis, conclusion, status}}]}
GET /search?q=love&corpus=kjv|egw|doctrine 全文/向量检索 {hits:[{source_type, source_id, ref, snippet, score}]}

5.3 牧师问答（模块 B）

方法 / 路径说明请求 / 响应（要点）
POST /qa/ask 提交问题，触发 RAG + 校验闸门 Req {question, locale?}
Res {answer_id, answer_zh, citations:[{source_type, source_id, ref, snippet}], confidence, needs_human}
闸门 needs_human=true 时 answer_zh 仅给引导语，转人工
GET /qa/{answer_id} 取历史问答 同 ask 响应体
POST /qa/{answer_id}/feedback 用户纠错 / 评分 {rating, comment?} → 进 qa_feedback + 必要时 review_queue

5.4 健康指导（模块 C）

方法 / 路径说明响应（要点）
GET /health/topics NEWSTART 八支柱 {topics:[{id, code, name_zh, summary}]}
GET /health/topics/{id}/guidance 某支柱指导条目（仅已审） {items:[{guidance_id, title, body_zh, evidence_level, sources:[source_id], disclaimer}]}
POST /health/log 每日打卡 {topic_code, metric_id, value, logged_at}
GET /health/log?from=&to= 打卡历史 {entries:[...]}

5.5 用户同步与审核（内部）

方法 / 路径说明要点
POST /sync 差量同步书签/笔记/打卡 {last_seq, changes:[...]} → {new_seq, applied}
GET /review/queue 顾问拉取待审（需 advisor 角色） {items:[{id, kind, payload, status}]}
POST /review/items/{id} 批准/驳回（需 advisor） {action:"approve|reject", note?} → 触发 content_version
契约纪律：接口路径、字段名、状态码以本表为唯一事实来源；前端 retrofit 客户端由本表生成；任何 breaking change 必须 bump /api/v1 到 /api/v2 并行过渡，不得静默改字段。

六、数据契约（对外 DTO 与落库对齐）

以下 DTO 直接映射 schema-and-rag 的落库表，确保「接口返回 = 数据库可溯源」。

// VerseView  →  bible_verse_kjv + bible_verse_zh + bible_verse_cuv_ref
{
  "ref": "Jn 3:16",
  "kjv_text": "For God so loved the world...",   // 权威来源（英文）
  "our_zh": "神爱世人……",                         // 本应用独立产出
  "cuv_ref_text": "神爱世人……"                     // 仅参照，不参与来源
}

// ComparisonNote  →  comparison_note（status 必须为 approved 才下发）
{
  "ref": "Jn 3:16",
  "diff_type": "archaic_kjv | mistranslation | text_tradition | consistent",
  "observation": "KJV 'whosoever' 古词，本应用译作'凡'……",
  "basis": "source_id:KJV-Jn3:16；希腊原文 pás",    // 必填
  "conclusion": "本应用与和合本此处一致，差异仅在 KJV 古词",
  "status": "approved | draft"
}

// QaAnswer  →  qa_answer + qa_citation
{
  "answer_id": "qa_8f2c",
  "answer_zh": "根据……（见【来源:BIBLE|Jn3:16】）",
  "citations": [{"source_type":"BIBLE","source_id":"KJV-Jn3:16","ref":"Jn 3:16","snippet":"..."}],
  "confidence": 0.82,
  "needs_human": false
}

// HealthGuidance  →  health_guidance（medical_reviewed 必须为 true）
{
  "guidance_id": "hg_12",
  "title": "每日饮水量建议",
  "body_zh": "……",
  "evidence_level": "A|B|C",
  "sources": ["EGW-MH-p123","BIBLE-..."],
  "disclaimer": "本内容不替代专业医疗诊断……"
}
一致性红线：DTO 里的 source_id 必须能在 content_chunk.source_id 或对应权威表中查到；前端展示引用时点击应跳转回 KJV/EGW/教义原文，形成「产出 → 来源」闭环。任何 cuv 前缀 id 绝不允许出现在 citations 中。

七、角色权限与鉴权

角色能力约束
anonymous浏览圣经/译文/对照/健康公开内容、检索无书签/问答/打卡；只读已 approved/medical_reviewed 内容
member上述 + 书签/笔记/问答/健康打卡/差量同步问答受闸门限制；不可见 draft 内容
advisormember + review_queue 审批 + 问答纠错复核只能批准/驳回，不可改权威原文
adminadvisor + 内容发布/回滚（content_version）+ 白名单管理所有发布动作留审计日志
鉴权：设备匿名 JWT（role=anonymous）→ 可选绑定账号升级 member；advisor/admin 须后台人工开通并 MFA。所有写操作（发布、审批、纠错）落入审计表，与内容版本化联动，支持回滚。

八、验收质量门禁

与 master-handbook 的「准确性校验机制」对齐，作为每个阶段 Done 的硬条件：

维度门禁指标阈值
溯源完整性对外中文内容可追 source_id 比例100%
引用必填问答 citations 非空率100%
臆测拦截无来源回答被闸门拦截率100%
置信兜底confidence < 0.70 转人工率100%
内容隔离citations 中出现 cuv/中文译本 id0（出现即拦截）
医学边界未 medical_reviewed 的健康条目可见率0%
离线可用首屏 + 圣经阅读断网成功率100%
崩溃率公测期客户端崩溃率< 1%
上线否决项（Go/No-Go）：① 法务白名单未签字；② 引用缺失率 > 0；③ 和合本 id 进入 citations；④ 未审健康条目漏出；⑤ 离线圣经不可用。任一不达标，禁止发布。

九、依赖与风险

  • 版权 最高优先级：法务裁定前不得上线任何 EGW/Tier 2 内容；英联邦 KJV 须走 ASV/WEB 替代开关。
  • 内容 权威库采集与中文译校是长链条，建议 P0 即启动，避免 M3/M4 因内容缺失阻塞。
  • 模型 自托管中文 LLM 显存/算力门槛；若外网云 API 须评估合规与数据出境风险，RAG 上下文含教义内容需脱敏或本地化。
  • 离线包 EGW 文库较大，离线包需分卷；首版可仅预置圣经+教义，EGW 按需下载。
  • 表述分寸 对照/纠正功能以释经观察呈现，避免论战化；comparison_note 经 advisor 双审。
